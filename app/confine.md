# 开发约束规范

## 1. 底层驱动与框架只读

- 不允许修改底层驱动代码、框架代码、BSP、中断处理、CMSIS 库。
- 若在开发过程中发现底层驱动存在问题或需要调整，**必须先向用户提问说明原因，等待授权后才能修改**。
- 绝对禁止在未获授权的情况下擅自修改以下目录或文件：
  - `Libraries/`
  - `Driver/`
  - `Components/`（BSP 部分）
  - `USER/src/gd32f4xx_it.c`（中断处理）
  - 所有 `startup_*.s` 启动文件

---

## 2. 通信模式

- 所有协议帧按十六进制结构组帧后，以**组帧后的 ASCII 字符串形式**在串口收发，不通过 Hex 字节发送。
  - 例：帧头为 `0xA5B6`，发送字符 `A5B6`（即字节 `0x41 0x35 0x42 0x36`），而非原始字节 `0xA5 0xB6`。
- 以下功能使用**纯字符串直接回复**，不经帧封装：
  - 告警查询
  - Bootloader 提示
  - 睡眠唤醒
  - （具体内容参见通讯协议文档）

---

## 3. 低耦合原则

- 新增业务功能统一放在 sysFunction/ 目录下；
- 每类功能尽量独立成模块，例如 sys_device、sys_param、sys_sample、sys_alarm、sys_ota；
- Protocol 层只负责解析命令和组帧，不直接写业务逻辑；Function 层通过公开接口被 Protocol 调用；
- 模块内部变量用 static 隐藏，头文件只暴露必要函数。

---

## 4. 代码分层目录规范

- **驱动层**（`Driver/`）：UART、IIC、SPI、OLED、Flash、RTC 等所有底层硬件驱动代码必须放置在 `Driver/` 文件夹下，允许在其内部按需建立二级子目录或直接放置文件。
- **协议层**（`Protocol/`）：帧解析、应答组帧、CRC 校验等通讯协议相关代码必须放置在 `Protocol/` 文件夹下。
- **业务逻辑层**（`Function/`）：采样、变比设置、阈值设置、告警、参数管理及业务逻辑判断等应用层代码必须放置在 `Function/` 文件夹下。
- 禁止跨层混放：驱动代码不得出现在 `Protocol/` 或 `Function/` 中，业务逻辑不得直接写入 `Driver/` 中。

---

## 4.1 通道数据上报规则

- 无论是**单次查询**还是**自动上报**，返回给上位机的通道数据必须是**原始采样值 × 当前变比**之后的结果。
- 变比由 `0x0241`（CH0）、`0x0242`（CH1）等命令在运行时配置，默认值为 `1.0f`。
- 业务层（`Function/`）负责完成"原始采样值 × 变比"的乘法运算，协议层（`Protocol/`）只负责把结果按 IEEE 754 大端打包进帧。

---

## 5. 单片机引脚未知时必须先询问

- 涉及具体引脚编号、复用功能、时钟来源、外设配置参数等硬件信息，若不确定，**必须先向用户提问，由用户提供准确信息**。
- 禁止自行猜测或编造引脚定义、寄存器地址、外设参数等硬件相关内容。
- 提问时应明确说明需要哪个外设的哪个参数，便于用户快速作答。

---

## 6. 优先使用已封装代码，确实无法满足时才另写

### 6.1 检索优先级

编写任何新功能或修改逻辑**之前**，必须先在工程中按以下优先级检索可复用的接口 / 宏 / 驱动：

1. `Function/`（应用层与 `sysFunction/` 自研模块）
2. `Driver/Components/`（BSP、OLED、按键、Flash、SDIO、FatFs 等组件封装）
3. `Driver/Libraries/`（GD32 标准外设库）
4. `PACK/`（perf_counter 等第三方扩展包）

检索完成后，再决定实现方式。**未做检索就动手写新代码的行为视为违规**。

### 6.2 复用规则

- 已有等价封装的，**必须直接调用**，禁止重复造轮子、禁止另写功能相同的"私有版本"。
- 常用封装示例（不完全列举，实际以工程为准）：

  | 需求 | 应调用的接口/宏 | 所在位置 |
  | --- | --- | --- |
  | OLED 显示字符串 | `OLED_ShowStr` / `oled_printf` | `Driver/Components/oled` / `Function/APP` |
  | OLED 清屏 | `OLED_Clear` | `Driver/Components/oled` |
  | 格式化串口输出 | `my_printf(DEBUG_USART, ...)` | `Function/APP/usart_app` |
  | 毫秒延时 | `delay_ms` | `PACK/perf_counter` |
  | 获取系统毫秒时间戳 | `get_system_ms` | `USER/systick` |
  | 按键状态读取 | `KEY1_READ` … `KEY6_READ` | `Driver/Components/bsp` |
  | LED 控制 | `LEDx_ON` / `LEDx_OFF` / `LEDx_TOGGLE` | `Driver/Components/bsp` |
  | SPI Flash 读写 | `gd25qxx_*` 系列接口 | `Driver/Components/gd25qxx` |
  | SD 卡 / 文件系统 | FatFs `f_*` 接口 | `Driver/Components/fatfs` |

### 6.3 现有封装不完全满足需求时

按以下顺序处理，**不得跳级**：

1. **包装组合**：在 `sysFunction/` 的新模块里调用现有封装，做参数组合、状态机、流程拼装等"业务层"工作。这是首选方案。
2. **接口扩展**：若确需新增对外接口，**先向用户说明缺口和方案，等待授权后再动手**；并优先扩展，而不是替换已有接口。
3. **另写实现**：仅在前两步均被验证不可行（且已获用户授权）的前提下，才允许自写底层；自写代码必须放在 `sysFunction/` 下作为独立模块，并在文件头注释中写明：
   - 为何不能复用现有封装；
   - 与现有封装的差异；
   - 来源（自写 / 参考资料 / AI 生成 / 第三方片段）。

### 6.4 禁止行为

- 禁止在不查看现有封装的情况下直接编写驱动级、外设级代码。
- 禁止以"风格统一"、"看起来更简洁"、"我更熟悉这种写法"为由绕过已有封装。
- 禁止把第三方 / AI 生成的代码片段直接粘贴进 `Driver/` 或已验证模块；如确需引入，按 6.3 第 3 条作为独立模块管理。
- 禁止擅自在已验证模块内追加 "辅助函数 / 私有补丁"——任何对已验证代码的改动都受第 4 条约束。
